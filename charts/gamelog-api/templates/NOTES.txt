The ingest API is running{{ if .Values.autoscaling.enabled }}, behind a HorizontalPodAutoscaler{{ end }}.

  kubectl -n {{ .Release.Namespace }} get pods -l app.kubernetes.io/instance={{ .Release.Name }}

Post one event and read it back:

  kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "gamelog-api.fullname" . }} {{ .Values.service.port }}:{{ .Values.service.port }} &
  curl -s -X POST localhost:{{ .Values.service.port }}/v1/events \
    -H 'content-type: application/json' \
    -d '{"events":[{"game_id":"demo","event_type":"session","player_id":"p1","value":1}]}'
  curl -s localhost:{{ .Values.service.port }}/v1/games/stats | head -c 300

Two things this chart does on purpose:

  * replicaCount is {{ .Values.replicaCount }}. The rollup worker starts in every replica and both
    would run the schema migrations at boot, so scaling out needs a lock first. docs/kubernetes.md
    explains what to change.
  * terminationGracePeriodSeconds is {{ .Values.terminationGracePeriodSeconds }} because the service
    flushes the events still in memory on SIGTERM, and it needs those seconds to finish the write.

{{- if not .Values.database.existingSecret }}

The database connection string lives in the Secret {{ include "gamelog-api.fullname" . }}. For
production point database.existingSecret at a Secret you rotate yourself.
{{- end }}

{{- if not .Values.waitForDatabase.enabled }}

No init container waits for the database: the service exits when Postgres is unreachable and
Kubernetes restarts it with backoff. Set waitForDatabase.enabled=true for a quieter first boot.
{{- end }}
